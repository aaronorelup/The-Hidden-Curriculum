# S212: Lovable docs, "Git sync" (with Glossary, Secrets and Custom domains)

**Credit:** Lovable, "Sync your Lovable project code with GitHub, GitLab, or Bitbucket" (Git sync overview), Lovable documentation (docs.lovable.dev). The page itself is undated live docs; re-read in full 2026-10-23 (Markdown version). URL: https://docs.lovable.dev/integrations/git-sync-overview.md. Companion pages in the same source entry: https://docs.lovable.dev/glossary.md, https://docs.lovable.dev/features/secrets.md, https://docs.lovable.dev/features/custom-domain.md (all re-read 2026-10-23; this lesson uses only the Git sync page plus one glossary line).

**What it is:** Lovable's own explanation of how a Lovable project syncs two ways with a repository on GitHub, GitLab or Bitbucket. It is product documentation, not a study. It has no measurements; its only number is "the 50 most recent commits" that the sync status card compares.

**Dates on the page:** "May 13, 2026" is not a page date. It is the date from which new Lovable apps use TanStack Start (it matters only for running the app locally). The page's newest feature, "Restore Lovable work after a push replaces it", is in Lovable's changelog under **Oct 5, 2026**. Bitbucket Cloud sync is dated **Sep 10, 2026** in the same changelog.

## What this lesson uses from it (checked against the page, 2026-10-23)

### C124.2: a branch is a name; the platform works on one of them
- Verbatim, in "How Git sync works": "Lovable edits and syncs **one branch at a time**. Commits on other branches don't appear in Lovable until you merge them into the synced branch or switch the synced branch." The spec's quote ("Commits on other branches don't appear in Lovable until you merge them into the synced branch") is exact but **cut**: the sentence goes on "or switch the synced branch". If it is shown on screen, show the whole sentence or end it with an ellipsis, so it is clear there are two ways to fix it.
- You can switch branches and create new branches from Lovable on all three providers. The synced branch is "usually `main`" (the repository's default branch by default, per the GitHub page).
- Lovable's advice on branches, verbatim in meaning: keep Lovable on the synced branch, do your own work on a feature branch, and "The feature branch stays out of your Lovable project until you merge it into the synced branch, so unreviewed work does not reach the project." This is a branch used for its real purpose, keeping unreviewed work off the line that matters.
- Two-way sync as stated: edits in Lovable are committed and pushed to your repository; commits pushed to the synced branch come back into Lovable. Lovable creates a **new** repository when you link a project (export only; you can't import an existing repository).
- Under "Limitations": "**One branch at a time.** Only commits on the synced branch appear in Lovable."

### C124.6: rewriting history (brief)
- Verbatim: "Do not force-push, rebase, or squash commits that are already on the synced branch." The spec quote is exact.
- What the page says happens if you do (this is the "why", and the spec leaves it out): "Lovable keeps its own copy of that branch. When you rewrite its history, the next sync saves a backup of Lovable's copy and then replaces it with yours. The project owner can restore the backup." Restore is a feature dated Oct 5, 2026 (changelog). Only the project owner can restore; the notice shows for 24 hours, after which the owner uses "Check for saved Lovable work".
- The page's safe alternative, verbatim: "To undo a change, add a commit that reverts it." This is the one-line recognition point for the lesson: undo by adding, not by rewriting.
- When the sync status reads "Lovable and GitHub have diverged", Lovable pushes its changes to a separate `lovable-sync` branch instead, and the next sync from GitHub replaces Lovable's version of the branch. A protected branch also sends Lovable's push to `lovable-sync`.
- From the commit-attribution section: "Lovable cannot rewrite Git history", so email addresses already pushed stay in the repository. Supporting only.

### C124.3 and C124.4: a remote is a copy elsewhere; pushing and publishing (supporting)
- The page lists "Back up your code. Store your project safely outside Lovable, in an account you control" as the first reason to sync. It also says "You don't need Git to use Lovable."
- FAQ, useful against a wrong mental model: "Does pushing to my repository update my live site? No. ... it never publishes. Your live site only changes when you publish from Lovable." In Lovable, the synced branch is what the editor sees, **not** what is live. See the spec issue below.
- The repository Lovable creates on GitHub is "**private by default**". This line is on the GitHub provider page (https://docs.lovable.dev/integrations/github.md), not on any of the four URLs in S212's entry. If the lesson uses it, add that URL to the S212 entry.
- "A Git branch does not give you a separate database." A local clone that keeps the `.env` configuration reads and writes the same backend as the published app. This belongs to keys, environments and deploys (C126/C127, other lessons). Here it is one line at most.

### C124.7: checkpoints are not git (supporting, optional)
- The Glossary defines **History** as "The chronological log of changes to your project", which lets you revert or bookmark checkpoints. It is Lovable's own version history, separate from Git sync. Its page (features/projects/history.md, not in S212's URL list) warns that reverting restores code only, not database data. This is a parallel to S101's "remote actions can't be checkpointed" if one is wanted; not required.

### Questions this lesson answers: "Why don't my changes show up in Lovable?"
- Answer from S212: the commits are on a branch other than the synced one. Merge them into the synced branch or switch the synced branch.
- The GitHub provider page (not in S212's URL list) gives a second cause: GitHub's push notification never arrived, the card shows "GitHub is N commits ahead of Lovable", and the fix is to push a new commit (even an empty one). Re-check and Reconnect don't pull anything.

## What the spec attributes to S212 that S212 does not say, or says differently
1. **"Builder platforms work the same way" (C124.2) mixes "the branch the tool works on" with "the branch that is live".** The spec puts the Lovable line right after "Which branch is live is a setting somebody chose" (AO-043). In Lovable, the synced branch is **not** what is live. The FAQ says pushing "never publishes" and the live site changes only when you publish. Correct framing: in Lovable, too, a setting picks which branch counts (the synced branch), and work on other branches is invisible to it until merged. Being live is a separate step, Publish.
2. **The spec's second quote is cut mid-sentence.** The original goes on "or switch the synced branch". Not wrong, but show the full sentence or use an ellipsis.
3. **"Rewriting history breaks the other copies" (C124.6) is stronger than what Lovable describes now.** Since Oct 5, 2026, Lovable saves a backup of its copy and the project owner can restore it. The damage is that Lovable's version is replaced and its work is lost until the owner restores it. The rule itself ("Do not force-push, rebase, or squash...") is unchanged and exact.
4. S212's entry in sources.md says the git-sync page "names 2026-05-13". That date is the TanStack Start cut-over for new apps, not a page or feature date. It is harmless but should not be shown as the source's date.
5. "Private by default", the troubleshooting causes and version History are on companion pages (github.md, projects/history.md), not on the four URLs in the entry. Add those URLs if the lesson uses them.
