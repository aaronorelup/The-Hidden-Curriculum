## What this lesson uses, checked against the source

### C117 point 7: checkpoints are not git (section "Rewind with checkpoints")
- "Every prompt you send that starts a turn creates a checkpoint. You can restore conversation, code, or both to any previous checkpoint." **Verbatim** (a tip box).
- Claude "automatically snapshots files before each change". Double-tap Escape or run `/rewind` to open the rewind menu: restore conversation only, code only, both, or summarize from a selected message.
- Checkpoints are saved with the conversation: you can close the terminal, resume later and still rewind. The page pitches them as a way to "try something risky" and rewind if it fails.
- Warning box, as the spec quotes it: "Checkpoints only track changes made through Claude's file editing tools. Changes made through Bash commands or external processes are not captured. This isn't a replacement for git." **Verbatim; confirmed exactly.**
- Elsewhere on the page "Bash" means shell commands in general (Claude runs shell commands through its Bash tool, on Windows too), so "a shell command" in the lesson is a fair plain-English rendering.

### C117 point 4 / You vs the agent: evidence is something you read (section "Give Claude a way to verify its work")
- "Have Claude show evidence rather than asserting success: the test output, the command it ran and what it returned, or a screenshot of the result." **Verbatim; confirmed exactly.**
- The sentence that follows gives the reason: reviewing evidence is faster than re-running the check yourself, "and it works for sessions you weren't watching." Usable as the "why" in narration.
- Context the source states: the paragraph closes a section whose main advice is to give Claude a check it can run (tests, a build exit code, a linter, a screenshot to compare); "Claude stops when the work looks done", and without a check "you become the verification loop". This matters for the currency rule: the source assigns running the check to the agent and reading the evidence to you, which is exactly the lesson's split.
- Failure pattern on the same page, "The trust-then-verify gap": Claude produces a plausible-looking implementation that misses edge cases; fix: "If you can't verify it, don't ship it." (Supports the framing to avoid "If the agent says it's done, I don't need to look at what it ran"; the deeper treatment belongs to done-is-a-claim.)

### Commits as a sentence to the agent (C124 point 1, supporting S206)
- The explore-plan-implement workflow ends with step 4 "Commit": "Ask Claude to commit with a descriptive message and create a PR", example prompt "commit with a descriptive message and open a PR". Confirms the spec's point that a commit is something you ask for in words. (The spec cites S206 for that line; S117 says the same and can back it.)
- Permission allowlists example: `git commit` as a tool you might pre-approve. Auto mode, from v2.1.283, is the built-in starting permission mode for interactive terminal and VS Code sessions; a classifier reviews most actions and blocks what looks risky. (Context only; what auto mode allows for git is S052's job in this lesson.)

### Diff as the thing a reviewer reads (supports C117 diff points)
- "Add an adversarial review step": a reviewer subagent in a fresh context "sees only the diff and the criteria you give it", and the bundled `/code-review` skill reviews the current diff. Useful only as one line that the diff is the unit of review; review itself is taught in checking-what-you-cant-read.

## What the spec says that the source does NOT say
- **The demo "a checkpoint rewind that restores an edit made with the file tool but not a file deleted through a shell command" is credited to S117, but S117 never mentions deleting files.** It only says Bash changes "are not captured". The detail that matters comes from the separate Checkpointing page: "Once Claude has edited a file with its file editing tools in your conversation, `/rewind` undoes changes that Bash commands make to that file afterward. A file that only Bash commands changed isn't tracked and stays as it is." So S117's warning is a simplification: a shell change to a file Claude had already edited with its file tool IS rewound. **For the demo to show what the spec wants, the shell-deleted file must be one Claude never touched with its file-editing tool in that session**; otherwise rewind may bring it back and the demo contradicts the narration. Credit the nuance to the Checkpointing page (add it to the source list if used), or keep the narration to S117's own sentence.
- The Checkpointing page also says snapshots are kept for the 100 most recent checkpoints and deleted about 30 days after the session last saved one (setting `cleanupPeriodDays`), and that edits by other concurrent sessions and manual edits outside Claude Code are normally not captured. Not in S117; not in the spec; usable as one line ("checkpoints expire, git history does not") only if credited to the Checkpointing page.
- S117 does not say checkpoints cannot undo remote actions (databases, APIs, deployments, pushes); that line is S101's, as the spec correctly attributes.
- S117 does not mention branches, remotes, push, `git log`, `git remote -v`, or the `+12 -1` indicator. Nothing in C124 points 2 to 5 rests on S117.
- S117 says "treat [sessions] like branches" (`/rename`) as a metaphor for workstreams; not git branches. Do not use it for C124 point 2.
- The sources.md "Contributes" line (check it can run; explore, plan, implement; interview mode; clear after two failed corrections) lists S117's uses in other lessons. Of those, this lesson uses none except the verification context above.
