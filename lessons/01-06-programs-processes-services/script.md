## 01 — The point
[[purpose]]In this lesson you'll learn the difference between a program on your disk, a process running it right now, and a service your computer keeps running in the background with no window. [[conclusion]]A program is a file of instructions. A process is one running copy of it. A service is a process the operating system starts and keeps alive by itself. [[three-shelves]]File, running copy, kept alive. [[one-idea]]"Port already in use", a server that outlived its window, an A I tool busy in the background: all one idea. [[your-part]]Your agent can find and stop those. Your part is knowing what ought to be running. [[notepad]]Aaron, who made this course, has an Information Systems degree, and once wrote Python in Notepad, saved as dot T X T, with no idea how to run it. [[sat-there]]It just sat there: a program that never became a process.

## 03 — The recipe and the cooks
[[shelf]]Picture a kitchen shelf of recipe cards. Each card is a program: instructions, doing nothing. [[cook]]A process is a cook working from one card, right now. [[ticket]]It gets a ticket number, called a process I D, or P I D. [[counter]]Its own stretch of counter, which is memory. [[satchel]]And the satchel handed over at the door by whoever sent it in: File Explorer, a terminal, an editor, an agent. That sender is its parent. [[same-card]]Many cooks can work from the same card at once. On the laptop this course is made on, eleven copies of node were running at one moment this month. One recipe, eleven processes.

## 04 — What a process really is
[[ingredients]]Under the picture, a process is private memory, a P I D, a copy of the environment, and an account it runs as, usually yours. [[threads]]Inside are threads: workers sharing its counter. That's module seven. [[count]]On the course laptop, at one moment, four hundred and fifty-seven processes were running. [[many-per-app]]One app is often several: a browser, V S Code, Ollama. [[breaks]]Here's where the kitchen breaks. A cook has judgement; a process follows its card exactly. [[cores]]Cooks really work side by side. A computer runs only as many processes at once as it has processor cores, and switches between the rest very fast. [[private]]And a cook can glance at a neighbour's counter. A process can't, unless the system lets it in, the way a debugger is.
> Screen labels only: private memory (walled off by default) · PID · environment · runs as you · threads. Threads depth: 07.01. "Runs as" depth: 01.07.

## 05 — The night staff: services and daemons
[[night]]Some cooks you never sent in. A service is a process the operating system's own manager starts, often at boot, with no window. [[no-one-home]]It can run with nobody signed in, and the manager can restart it if it stops. [[svchost]]On Windows, many services share one host program, shown as Service Host. On the course laptop, a hundred and sixty-six services were running; ninety-seven Service Host processes carried many of them. [[daemon]]On a Mac or Linux, the same idea is called a daemon. [[tray]]In between sits the tray app: it arrives when you sign in and leaves when you sign out. On Windows and Mac, Ollama is one of those, not a service. [[three-kinds]]Three kinds of cook: apps you open, tray apps that clock in with you, and night staff the building hires.
> Screen labels: Service Control Manager · svchost.exe · systemd (Linux) · launchd (Mac). Observed: 97 svchost.exe, 166 of 324 installed services running (separate counts: many running services, e.g. NVIDIA, ASUS, the Codex sandbox service, run as their own .exe, not inside svchost). Depth: 01.08, 16.01.

## 06 — Task Manager: the staff board
[[shortcut]]Every kitchen keeps a staff board. On Windows, it's Task Manager: Control, Shift, Escape. Five years ago, it was mostly for ending a frozen app. [[processes-tab]]The Processes tab groups every cook: apps, background processes, Windows processes. [[details]]Details gives one row per process, with its P I D. [[services-tab]]Services lists the night staff; Startup apps, who clocks in when you sign in. [[end-task]]End task stops a process at once. Whatever it hadn't saved is gone. [[new-columns]]Newer Windows 11 builds add two hidden columns you can switch on: N P U, which process uses the A I chip, and Isolation, for apps running fenced in. [[elsewhere]]On a Mac, the board is Activity Monitor; on Linux, top or h top.
> Task Manager redesign: Windows 11 22H2, Sept 2022 (no need to say it). NPU and Isolation columns: rolled out June 2026, hidden by default, NPU only on PCs with one (the course laptop has none). Draw from a mock-up, not a claimed screenshot. Screen label for Linux also: systemctl.

## 07 — Closing the window isn't ending the process
[[door]]A window is a door to the cook, not the cook. Close the door, and the cook can still be at the counter. [[outlive]]Three kinds keep working: tray apps like Ollama; services, which never had a door; and children whose parent went away. [[no-tree]]On Windows, ending a parent doesn't automatically end what it started. Tools that want to stop everything they launched have to group those processes first. [[tm-bug]]Late last year, a Windows update briefly made Task Manager itself keep running after you closed it. Microsoft fixed it in November.
> Screen label only: job object (Windows' name for the group). Bug: KB5067036 (2025-10-28), fixed November 2025; no KB number on screen.

## 08 — Servers and ports: one cook per hatch
[[hatch]]A server is a process that stays running and waits at a numbered serving hatch, called a port, for orders. [[one-per-hatch]]Only one process can hold a port at a time. [[numbers]]Numbers you'll often see: three thousand for many Node apps, fifty-one seventy-three for Veet, eight thousand for Python, eighty-one eighty-eight for ComfyUI, twelve thirty-four for L M Studio, and eleven four three four for Ollama. [[localhost]]Localhost means your own machine. [[listeners]]On the course laptop, twenty-seven hatches were open at once.
> Ports are "numbers you'll often see", not rules. Depth: 09.02, 09.03.

## 09 — The surprises: port in use, leftovers and "zombies"
[[eaddrinuse]]Node says: address already in use, port three thousand. [[meaning]]A cook is already at that hatch, usually an earlier copy you thought you stopped. [[vite-hop]]Veet's version is quieter. It says port fifty-one seventy-three is in use, trying another one, and opens fifty-one seventy-four. Now two copies run, and your browser may still show the old one. [[ollama-bind]]Start a second Ollama, and it can't take its port. [[zombie]]People call that leftover a zombie. Strictly, a zombie has already finished: just an entry the system keeps until its parent collects it, using nothing. [[orphan]]The thing holding your port is alive. It's a leftover, or orphan, whose parent is gone.
> Exact texts on screen, one at a time: `Error: listen EADDRINUSE: address already in use :::3000` · `Port 5173 is in use, trying another one...` · Ollama: a bind error on 127.0.0.1:11434 (label, not a quoted message).

## 10 — The lantern: model servers on your own machine
[[then]]Five years ago, a builder ran maybe one dev server, in a terminal they opened themselves. [[now]]Now A I tools start their own. [[model-server]]A local model server is just a long-running process on a localhost port. [[ollama-pair]]On the course laptop, Ollama's tray app is the parent of the Ollama server, at port eleven four three four. One app, two programs, two processes. [[keep-alive]]By default it keeps the model loaded for about five minutes after your last question, so that memory stays taken. [[others]]L M Studio and Microsoft's Foundry Local run windowless servers too. [[no-password]]Ollama's server has no password by default: fine on localhost, risky opened to the network, and researchers have found many exposed online.
> Dated on screen if wanted: Ollama for Windows preview Feb 2024 · LM Studio llmster Jan 2026 (port 1234) · Foundry Local GA Apr 2026. No version numbers, no exposure counts. Depth: 01.10, 09.08.

## 11 — The lantern: M C P servers are cooks your app hires
[[mcp-hire]]When your A I app opens, it hires a crew. Each local M C P server in its config is a child process the app launches. Five servers, five extra cooks, often node or python. [[inherit]]They get the satchel the app packs, often with keys in the config, and run with your permissions. [[shutdown]]When the app closes, it's meant to stop them, politely, then by force, and it should restart one that crashes. [[remote]]A remote one is somebody else's cook, in somebody else's kitchen. [[config-is-command]]This year, researchers stressed that a local M C P config line is, in effect, a command to run. The makers call that by design; their docs advise caution. Treat adding one like installing software.
> MCP announced 2024-11-25; current spec revision 2026-07-28 ("SHOULD restart"). OX Security, April 2026: no figures. Depth: 10.08, 10.09; supply chain 05.08, 10.12.

## 12 — The lantern: agents start processes for you
[[agent-children]]A coding agent is a head cook sending in helpers. Every command it runs is its own child process, so a dev server it starts belongs to the agent. [[background]]Long commands go to the background. In Claude Code, slash tasks lists them, and it says it cleans them up when it exits. Not every tool does. [[fences]]What's new is fences: sandboxes limiting what its commands and their children can touch. As of this month, Claude Code's sandbox covers Mac, Linux and W S L two, not native Windows. Codex's Windows sandbox also stops leftover child processes. [[mxc]]And Microsoft's Execution Containers, a way to fence agents in on Windows, became generally available this month. Some agents use them already; others say they will. [[isolation]]Task Manager's Isolation column shows only the fences built on Windows' app containers. [[heading]]Vendors are moving toward agents as their own kind of process, with their own account.
> Dated: Claude Code GA 2025-05-22; Claude Code sandbox 2025-10-08; Codex Windows sandbox 2026-03-04; MXC GA 2026-10-07 (process, session and WSL containers). Do not list Claude Code as an MXC user. Sandbox coverage changes often. Depth: 03.08, 14.12.

## 14 — Your job: judge what's running
[[your-job]]The agent can find a process and stop it. Your job is to judge what should be running, with five questions. [[q-what]]Is it a file, a running copy, or a service that comes back after a restart? [[q-who]]Who started it: you, a terminal, an agent, a tray app, or the system? [[q-port]]Which port does it hold? [[q-keys]]Does it carry your keys? [[q-fence]]And is it fenced in, or running with your full access? [[board]]Whoever started it, the system's board shows nearly every process; W S L and virtual machines show as one row.

## 16 — Keep this
[[keep-1]]Keep this. A program is a recipe; a process is a cook using it. One file can run many times, each with its own number, memory and settings. [[keep-2]]A service is a process the system keeps alive with no window. Closing a window doesn't end a process, and "port already in use" usually means an old copy holds the hatch. [[keep-3]]Your A I tools are processes too. They run as you, with your keys. Know what should run, and whether it's fenced in.
