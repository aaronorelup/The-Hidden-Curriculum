# research-now: Programs, processes & services (as of 2026-10-11)

Lens: the subject as a learner meets it THIS month (October 2026): current mechanisms, names, versions, screens and error texts, and how AI tools now start, keep and contain processes.
Status tags: **established** / **new this year** (roughly Oct 2025 to Oct 2026) / **beta or announced** / **speculation** / **observed** (seen directly on Aaron's Windows 11 laptop on 2026-10-11, via Get-Process / Get-Service / Get-NetTCPConnection).
Orchestrator names checked: all names in the notes are real and current. "Zombie process" has a strict Unix meaning (section 7) that differs from how people use it for leftover dev servers; say which one is meant. "Daemon" = the Unix/macOS word for what Windows calls a service. "MCP servers" are now covered by spec revision **2026-07-28** (not 2025-06-18 or 2025-11-25).

## 1. Program vs process: a file of instructions vs one running copy

- A process is the container of resources needed to run a program: "a virtual address space, executable code, open handles to system objects, a security context, a unique process identifier, environment variables, a priority class ... and at least one thread of execution." Each process starts with one thread and can create more. Status: established. Source: Microsoft Learn, "About Processes and Threads", https://learn.microsoft.com/windows/win32/procthread/about-processes-and-threads (Win32 docs, undated page; content long-standing).
- A thread is "the entity within a process that can be scheduled for execution"; all threads of a process share its memory. Several threads run truly at once only up to the number of logical processors; the rest is fast switching (preemptive multitasking). Status: established. Same source.
- So: one program file (e.g. `chrome.exe`, `node.exe`) can be running as many processes at once, each with its own PID, memory and environment. Status: established. Observed: 11 `node` processes, 14 `claude` processes, 5 `python` + 3 `pythonw` processes running at once on Aaron's laptop.
- Child inherits a COPY of the parent's environment (link back to 01.05): that is why an agent's subprocess sees the same API keys as the agent. Status: established. Source: Microsoft Learn "Environment Variables", https://learn.microsoft.com/en-us/windows/win32/procthread/environment-variables (ms.date 2025-07-14); Claude Code sandbox docs list "Environment variables: Inherited from Claude Code, including any secrets in its environment", https://code.claude.com/docs/en/sandboxing (live docs, fetched 2026-10-11).
- "Job objects" let Windows manage a group of processes as one unit (kill the group together). Relevant because MCP and coding-agent sandboxes use them to clean up child processes. Status: established. Source: About Processes and Threads (above); MCP stdio spec names Job Objects for Windows shutdown (section 5).
- Scale on a normal PC: **observed** 457 processes, 7,323 threads, 97 of them `svchost.exe`, on Aaron's laptop at 2026-10-11. A ready-made "you have hundreds of these" number.

## 2. Services and daemons: processes the OS starts and keeps alive without a window

- Windows: a service application "conforms to the interface rules of the Service Control Manager (SCM). It can be started automatically at system boot, by a user through the Services control panel applet, or by an application ... Services can execute even when no user is logged on." Start can also be by triggers. Status: established. Source: Microsoft Learn "Services", https://learn.microsoft.com/en-us/windows/win32/services/services (updated 2025-04-15).
- Many Windows services share a host process, `svchost.exe` ("Service Host: ..." rows in Task Manager); `tasklist /svc` shows which services sit in which svchost PID. Status: established. Sources: https://www.ionos.com/digitalguide/server/know-how/svchostexe/ (undated); https://helpdeskgeek.com/how-to/svchost-exe-process-in-windows/ (undated).
- **Observed:** 324 services installed, 166 running; services seen include `CodexSandboxService.OpenAI.Codex` (display name "ChatGPT", Running), `MicrosoftCopilotElevationService` (Stopped), `WSAIFabricSvc` (display name "Windows AI Components Host", Running), NVIDIA and ASUS Armoury Crate services.
- Linux (systemd): what systemd calls a "service" was historically called a daemon, "any program that runs as a background process (without a terminal or user interface)"; a *service unit* file says how to start/stop it, when to auto-start it, and its dependencies. Status: established. Sources: Arch Wiki "Daemon", https://wiki.archlinux.org/title/Daemon (live wiki); https://www.computernetworkingnotes.com/linux-tutorials/systemd-units-explained-with-types-and-states.html (undated).
- macOS (launchd): `launchd` starts at boot and manages jobs; *launch daemons* (`/Library/LaunchDaemons`, run as root/system, no UI) vs *launch agents* (`~/Library/LaunchAgents`, run for the logged-in user, may show UI); controlled with `launchctl`. Status: established. Source: TechRepublic, https://www.techrepublic.com/article/macos-know-the-difference-between-launch-agents-and-daemons-and-use-them-to-automate-processes/ (undated; verify against `man launchd.plist`).
- A middle category the learner will meet constantly: **login items / startup apps** (tray apps started when you log in). They look like services but are ordinary user processes started by the shell, and stop when you log out. Ollama on Windows is one (section 4). Status: established. Source: Ollama FAQ, https://docs.ollama.com/faq ("Ollama for Windows and macOS register as a login item during installation", live docs, fetched 2026-10-11).

## 3. Task Manager tour (Windows 11, October 2026)

- Layout since the 2022 redesign: left-hand navigation (Processes, Performance, App history, Startup apps, Users, Details, Services), dark mode, settings page, **Efficiency mode** (lowers a process's priority/CPU use), filter box (by name, PID or publisher; Alt+F). Status: established. Sources: BleepingComputer "Closer look at Windows 11's new Task Manager", https://www.bleepingcomputer.com/news/microsoft/closer-look-at-windows-11s-new-task-manager/ (2022); TechRadar search-bar report, https://www.techradar.com/news/rejoice-task-manager-is-finally-getting-a-search-bar-in-a-future-windows-11-update (2022). Note: no Microsoft support page listing the tab set was found this pass; tab names confirmed by Aaron's machine (observe on screen before animating).
- Processes tab groups rows into **Apps** (have windows), **Background processes**, **Windows processes** (largely Service Host rows). Right-click > "Go to details" jumps to the Details tab with the PID. Status: established. Source: https://www.online-tech-tips.com/?p=215 (undated); helpdeskgeek (above).
- Details tab = one row per process with PID, status, user, CPU, memory (the "real" process list). Services tab = SCM's list with PID of the hosting process and Running/Stopped. Status: established. Same sources.
- **CPU numbers changed in Aug 2025:** Processes tab now uses the same formula as Performance/Users tabs and third-party tools, (delta process CPU time) / (delta elapsed time x logical processors); old value kept as optional "CPU Utility" column in Details. Shipped in KB5064081 (build 26100.5074, 2025-08-29). Status: new this year (just outside 12 months; current behaviour). Source: https://www.bleepingcomputer.com/news/microsoft/windows-11-kb5064081-update-clears-up-cpu-usage-metrics-in-task-manager/ (2025-08).
- **NPU columns (2026):** optional "NPU" and "NPU engine" columns on Processes, Users and Details; "NPU dedicated/shared memory" on Details; GPU-integrated neural engines on the Performance page; plus an optional **"Isolation"** column showing apps running in an AppContainer. All hidden by default (right-click a column header). Preview KB5089573 (2026-05-26, builds 26100.8524 / 26200.8524), broad rollout KB5094126 (2026-06-09). NPU views appear only on machines with an NPU. Status: new this year. Sources: https://www.it-connect.tech/is-your-pc-really-using-its-npu-windows-11-can-now-tell-you/ (2026-08-20); https://anavem.com/news/kb5089573-adds-shared-audio-npu-task-manager-and-faster-shell-to-windows-11 (updated 2026-07-19); Neowin, https://www.neowin.net/amp/windows-11-gets-big-performance-upgrade-shared-audio-support-and-more-in-new-update/ (2026-05). Aaron's laptop (RTX 4070, no NPU) will not show NPU graphs.
- "End task" in the taskbar right-click menu: off by default, enable in Settings > System > For developers (location moved between builds; search "End task"). Uses the same force-terminate as Task Manager; unsaved work is lost; does not cover Explorer/system processes. Exact scope (whole process tree vs same-name processes) is reported differently by outlets; no Microsoft doc found. Status: established (feature since 2023). Sources: https://bleepingcomputer.com/news/microsoft/windows-11-taskbar-has-a-hidden-end-task-feature-how-to-turn-it-on (2023); https://windowslatest.com/2025/04/20/windows-11s-end-task-button-for-taskbar-is-the-best-feature (2025-04-20).
- Power-user alternative still current: Sysinternals **Process Explorer** (process tree, handles, DLLs per process), page updated 2026-09-10, runs on Windows 11+. Status: established. Source: https://learn.microsoft.com/en-us/sysinternals/downloads/process-explorer (published 2026-09-10).
- macOS equivalent: Activity Monitor; Linux: `top`/`htop`/`ps`, `systemctl status`. Status: established (no new source needed; general knowledge, flag if quoted on screen).

## 4. Local model servers: Ollama, LM Studio, Foundry Local

- Ollama binds `127.0.0.1:11434` by default; change with `OLLAMA_HOST`; models stay loaded in memory 5 minutes after last use (`OLLAMA_KEEP_ALIVE`); `ollama stop` unloads a model; on Windows you quit the tray app. On Windows/macOS it is a **login item**, not an OS service; on Linux it is typically a **systemd service**. Status: established. Source: Ollama FAQ, https://docs.ollama.com/faq (fetched 2026-10-11).
- **Observed process tree on Aaron's laptop:** `ollama app.exe` (PID 1168, the tray app) is the parent of `ollama.exe` (PID 22124, the server), which listens on 127.0.0.1:11434; the tray app itself listens on another localhost port (60398). A clean "one program, two processes, parent and child, one port" visual.
- The API has no authentication by default; exposing it beyond localhost is a known risk. Status: established. Source: https://bestllmfor.com/guides/ollama-serve-service-guide/ (2026-09, third-party).
- Current Ollama: v0.40.3 (2026-10-11, "Latest"); 0.40.x recent changes include background model upgrades (0.40.2) then paused (0.40.3), cloud usage proxying (0.40.1); 0.34.2 added shared first-run setup with the desktop app on Windows/macOS. Version numbers move weekly: say "Ollama", not a version. Status: new this year. Source: https://github.com/ollama/ollama/releases (fetched 2026-10-11).
- LM Studio: headless daemon **`llmster`** (`lms daemon up`, `lms server start`), API on port **1234** (same as the desktop app); docs give a systemd unit to run it at boot on Linux; desktop app can "run the LLM server on login". Status: new this year (llmster naming). Sources: https://lmstudio.ai/docs/developer/core/headless_llmster (live docs); https://lmstudio.ai/docs/app/basics/lmstudio-vs-llmster-vs-lms (live docs).
- Microsoft **Foundry Local** GA 2026-04-09: local model runtime on Windows ML, optional OpenAI-compatible HTTP endpoint. **Windows ML** GA 2025-09-23 (Windows App SDK 1.8.1, Windows 11 24H2+). Status: new this year. Sources: https://devblogs.microsoft.com/foundry/foundry-local-ga/ (2026-04-09); https://blogs.windows.com/windowsdeveloper/2025/09/23/windows-ml-is-generally-available-empowering-developers-to-scale-local-ai-across-windows-devices (2025-09-23).
- Mental-model point: a "local model server" is just a long-running process listening on a localhost port; whether it's a service, a login item or a terminal window decides who starts it and whether it survives logout/close. Status: established (synthesis of the above).

## 5. MCP servers: processes your AI app starts (stdio) or talks to (HTTP)

- Current MCP spec revision is **2026-07-28** (previous: 2025-11-25). Two standard transports: **stdio** ("the client launches the MCP server as a subprocess"; JSON-RPC lines over stdin/stdout; stderr for logs) and **Streamable HTTP** (each message an HTTP POST to one endpoint; server runs on its own). Status: new this year. Source: https://modelcontextprotocol.io/specification/2026-07-28/basic/transports and .../transports/stdio (fetched 2026-10-11).
- Lifecycle rules worth showing: client shuts down a stdio server by closing its stdin, waiting, then force-killing (SIGTERM then SIGKILL on POSIX; `TerminateProcess` or Job Objects on Windows). If the server dies unexpectedly the client SHOULD restart it. Status: new this year (wording in 2026-07-28; same idea since 2024-11-05). Same source.
- 2026-07-28 made MCP **stateless**: removed the `initialize` handshake and protocol sessions (`Mcp-Session-Id`); each request carries version/capabilities; new `server/discover`; HTTP+SSE transport formally Deprecated. Consequence for this lesson: a crashed-and-restarted stdio server loses nothing protocol-wise. Status: new this year. Source: https://modelcontextprotocol.io/specification/2026-07-28/changelog (fetched 2026-10-11).
- So a learner with five MCP servers configured in Claude Desktop / Claude Code / Cursor has five extra child processes per app (often `node`/`npx`/`uvx`/`python`), started with the app's environment. Status: established (follows from stdio spec + env inheritance). Observed: `claude.exe` has `uv.exe` among its children on Aaron's laptop.
- Security: April 2026, OX Security reported that stdio MCP config means "run this command" in Anthropic's official SDKs (Python, TypeScript, Java, Rust): the configured command runs even if no valid MCP server starts; downstream CVEs (e.g. LiteLLM CVE-2026-30623, Windsurf CVE-2026-30615). Anthropic called it by design and updated SECURITY.md to say stdio adapters should be used "with caution". Status: new this year. Sources: SecurityWeek, https://www.securityweek.com/by-design-flaw-in-mcp-could-enable-widespread-ai-supply-chain-attacks/ (2026-04-15); OX Security, https://www.ox.security/blog/the-mother-of-all-ai-supply-chains-critical-systemic-vulnerability-at-the-core-of-the-mcp (2026-04). Figures (150M downloads, 200k instances) are OX's own; hedge them.
- Claude Code: local MCP servers, hooks, LSP servers and status-line commands "run with your full access", outside the Bash sandbox. Status: established/current. Source: https://code.claude.com/docs/en/sandboxing (fetched 2026-10-11).
- Windows: "agent connectors" in Windows 11's experimental agentic features are MCP servers registered on the PC (On-device Registry); Agent Workspace runs agents in a separate Windows session under their own account. Off by default, admin must enable; Insider preview since Nov 2025. No GA announcement found. Status: beta or announced. Source: Microsoft Support "Experimental Agentic Features", https://support.microsoft.com/en-us/windows/ai/ai-features/experimental-agentic-features (first published 2025-10-16, updated 2025-12-05).

## 6. Coding agents spawning subprocesses (and containing them)

- Claude Code runs shell commands as child processes; long ones go to the **background** (prompted, `Ctrl+B`, or automatically when a command hits its timeout), get a task ID and an output file; `/tasks` lists running shells and subagents. Background tasks are cleaned up when Claude Code exits (on macOS/Linux including detached children), killed if output exceeds 5 GB; local interactive sessions have no time limit, unattended (`-p`, cloud) sessions do. `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` turns it off. Typical backgrounded commands named in the docs: vite, webpack, npm/pnpm. Status: new this year (current behaviour; details changed through 2026). Source: https://code.claude.com/docs/en/interactive-mode (fetched 2026-10-11).
- User reports of orphaned/long-lived background shells (e.g. tasks from earlier sessions still running 177-268 hours) exist on GitHub; treat as anecdotes. Status: speculation/anecdotal. Source: https://claudeissues.com/issue/67668-bug-background-bash-tasks-started-with-run-in-background-true-in-previous-sessio (2026, issue mirror).
- Claude Code sandbox: OS-enforced limits (Seatbelt on macOS, bubblewrap on Linux/WSL2) on files and network, which apply to Bash/PowerShell commands "and the processes they start". **On native Windows, Claude Code runs commands unsandboxed** (use WSL2 for the sandbox). Status: current. Source: https://code.claude.com/docs/en/sandboxing (fetched 2026-10-11).
- OpenAI Codex on Windows: native Windows sandbox (launched with the Codex Windows app, 2026-03-04) with modes MXC (recommended where supported), elevated (separate low-privilege sandbox users, firewall rules) and unelevated (restricted token); enforces limits "for commands and their child processes", and "remaining child processes stop when the foreground command exits" (so detached dev servers die). Status: new this year. Sources: https://learn.chatgpt.com/docs/windows/windows-sandbox.md (live docs, fetched 2026-10-11); Neowin, https://www.neowin.net/news/openai-releases-the-much-awaited-codex-app-for-windows/ (2026-03). Observed: `CodexSandboxService.OpenAI.Codex` service and `codex-windows-sandbox-service` process running on Aaron's laptop.
- **Microsoft Execution Containers (MXC):** policy-driven containment for AI agents on Windows (process containers via AppContainer; session containers in a separate Windows session/account; WSL containers; MicroVMs experimental). Announced as early preview at Build 2026 (Windows Developer Blog 2026-06-02); **GA announced 2026-10-07** for process, session and WSL containers; Intune management still coming. Supporting agents: GitHub Copilot, OpenAI Codex, OpenClaw, Replit, LM Studio, NVIDIA OpenShell, Unsloth; Claude Code, Manus, Perplexity "planned". Status: new this year (GA days old; MicroVM = beta). Sources: https://blogs.windows.com/windowsdeveloper/2026/06/02/windows-platform-security-for-ai-agents/ (2026-06-02); eSecurity Planet, https://www.esecurityplanet.com/endpoint-security/news-microsoft-execution-containers-for-ai-agents-reach-ga/ (2026-10-09). Ties to Task Manager's new "Isolation" column (section 3).
- Direction of travel: from "the agent's commands run as you, with everything you can touch" (2023-2024) to OS-level process containment per agent (2025-2026). Expect more agents to ship inside MXC/Seatbelt/bubblewrap boundaries. Status: speculation for the forecast; the shift itself is sourced above.

## 7. "Port already in use", leftover dev servers, zombies and orphans

- A dev server is a long-running process listening on a port (Vite default **5173**; many Node apps 3000; Ollama 11434; LM Studio 1234). Only one process can listen on a given address+port. Status: established. Source: Vite server options, https://vite.dev/config/server-options (live docs).
- Vite does NOT fail when 5173 is taken: it logs "Port 5173 is in use, trying another one..." and moves to the next free port unless `strictPort: true`, in which case it errors "Port 5173 is already in use". Result: two copies running, browser pointing at the old one. Status: established. Sources: vite.dev/config/server-options; source mirror https://repos.supermodeltools.com/vite/fn-http-ts-httpserverstart (secondary).
- Node's error: `Error: listen EADDRINUSE: address already in use :::3000`; usual cause is a previous instance not properly stopped (crash, closed terminal tab, agent background task). Status: established. Source: https://oneuptime.com/blog/post/2026-01-25-fix-eaddrinuse-nodejs/view (2026-01-25).
- **Observed:** Aaron's laptop has 27 localhost listeners at once (Ollama 11434, ComfyUI-style python on 8188, two `node` servers on 9100 and 18789, plus ASUS/Logitech/Steam helpers). Good visual: ports are numbered doors, each owned by one PID.
- Strict meaning of **zombie** (Unix/Linux/macOS): a child that has exited but whose entry stays in the process table until the parent reads its exit status (`wait`); it uses no CPU/memory beyond its PID entry and can't be killed (it's already dead); fix by fixing/ending the parent. An **orphan** is a still-running child whose parent died; it is re-parented to init/PID 1 (or a subreaper). Status: established. Source: Wikipedia "Zombie process", https://en.wikipedia.org/wiki/Zombie_process (live).
- What builders usually call a "zombie dev server" is really an **orphan**: still running, still holding the port, parent terminal or agent gone. Status: established (terminology). Same source.
- Windows has its own kind of zombie: a process that has exited but whose kernel object is kept alive by an open handle; Task Manager and Process Explorer don't show it. Status: established. Source: https://scorpiosoftware.net/2022/05/14/zombie-processes/ (2022-05-14).
- Windows does not automatically kill children when a parent exits (no tree kill by default); "End task" on a parent may leave children holding ports unless the tool kills the tree or uses a Job Object. Status: established (mechanism); see MCP spec's Job Objects advice and Codex sandbox "remaining child processes stop" behaviour above as the counter-measure.

## 9. What the learner judges (agents do the debugging)

- The judgement questions the docs above support: Is it a program on disk, a process running now, or a service that will come back after a restart/login? Who is its parent (terminal, agent, tray app, SCM)? Which port does it hold? Does it carry my keys (inherited env)? Is it contained (Isolation column, sandbox) or running with my full access? ## Traps (commonly said, now wrong or misleading)

- "Closing the terminal / the agent stops everything it started." Not reliably: Windows doesn't tree-kill by default; detached processes and background tasks can outlive their parent (Claude Code cleans up on exit, Codex sandbox kills leftover children, but tools vary).
- "A zombie process is a hung/leftover process eating your CPU." Strictly a zombie is already dead and uses nothing but a PID slot; the thing holding your port is an orphan or simply a still-running copy.
- "Ollama runs as a Windows service." On Windows and macOS it is a login/tray app (`ollama app.exe` parent of `ollama.exe`); only on Linux is it usually a systemd service.
- "Port in use means something else crashed." With Vite it may mean the opposite: the old one is still running and Vite quietly started a second copy on 5174.
- "MCP servers are remote web services." Most local ones are stdio child processes your AI app launches with your full permissions and environment; stdio config is literally a command to run (OX Security, April 2026).
- "The MCP handshake is `initialize`." Removed in spec 2026-07-28 (stateless; `server/discover`); old servers still use it.
- "Task Manager's CPU % on the Processes tab differs from other tools." Fixed Aug 2025 (KB5064081); now the same formula everywhere, old value in the optional "CPU Utility" column.
- "Task Manager can't show AI hardware." Since June 2026 it has optional NPU columns and an Isolation (AppContainer) column; hidden by default, NPU only on NPU machines.
- "Claude Code sandboxes commands on Windows." Native Windows runs commands unsandboxed; the sandbox needs macOS, Linux or WSL2 (MXC integration for Claude Code is announced, not shipped).
- "Agent sandboxes on Windows are experimental." MXC process/session/WSL containers went GA 2026-10-07; only MicroVMs are experimental.
- "Services are only old system stuff." AI vendors now install services too (Codex sandbox service, Copilot elevation service, Windows AI Components Host).
